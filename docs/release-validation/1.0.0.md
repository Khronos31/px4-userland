# PX4 1.0.0 検証記録

安定して再利用する候補取得・受信・CARD・USB・LNB・cleanup手順は [`../release-validation.md`](../release-validation.md) を正本とする。本書は1.0.0で確認できた結果と未達を記録し、未実施の項目を合格扱いしない。

## 1.0.0 問題発見試験の実績

これは最終1.0.0 candidate archiveのnative matrixではない。PX4 source `591685d89c6eb5283a322f508fa58b2c3759760e` とCore `154e9de7b813cee3cd9db07f22795a4a9e9ae833` のlocal build-qaで、PX-Q3U4の代表Linux x86_64にT27を2時間連続取得し、全対象channelの短時間受信も実施した。PX4 T27は82,646,892 packets / 15,537,615,696 bytes、client/daemon exit 0、sync/TEI/continuity/drop/USB/empty counters 0。8 receiver同時受信も行った。ここに記録した実測機種はPX-Q3U4であり、PX4の初回手順はPX-M1UR、PX-S1URを含む各機種に個別適用する。これらのlocal build結果を最終candidate archiveの合格へ読み替えない。

実施した2時間capture command:

```sh
px4-ts --instance qa-fixed-px4 --runtime-dir /tmp/3pr/px4rt \
  --receiver 2 --channel T27 --time 7200 --output /dev/null
```

### Linux musl x86_64 配布candidateの限定受信

source `591685d89c6eb5283a322f508fa58b2c3759760e` / Core `154e9de7b813cee3cd9db07f22795a4a9e9ae833`、Actions run `40152989770` の`linux-musl-x86_64` artifact `12583104365`（package SHA-256 `4e276ec299dd594d2da30acca32c9a1329307fd53d2885a7b6a65875e9cb96d0`）を使い、Q3U4でT27を8秒→600秒→8秒取得した。10分captureは`px4-ts --device usb:1-4.1.1,1-4.1.2 --instance musl-px4 --receiver 2 -c T27 -t 600 -o /dev/null --runtime-dir <runtime>`。実時間601.898秒、client exit 0、6,871,501 packets / 1,291,842,188 bytes、sync/TEI/client-CC/drop/USB/empty counters 0。事後8秒TSのanalyzerはexit 0、TSID 32736、PAT/PMT・A/Vあり、invalid sync/transport error/PID discontinuity 0。daemonは通常SIGINT exit 0、runtime socketとUSB ownerなし。

これはmusl配布archive上のT27単一受信だけの実測である。最大同時受信、3波、受信中status/反復APDU、CARD/USB物理挿抜を行った結果ではない。

物理確認ではCARD query、LNBの0→15→0V実測、停止後の再接続と新daemonでの短いT27受信が成功した。一方、受信中USB抜去後52.486秒でclient/daemonは自然終了せずstatusが残った。通常SIGINT時はclient exit 7、daemon exit 70/INTERNAL cleanup NOT_READY。別の初回PC/SC probeはB-CAS initに失敗した。手順/未達は[`initial-model-checks.md`](initial-model-checks.md)に記録する。

### Linux glibc x86_64 配布candidateの最大同時受信

Actions run `40152989770` / artifact `12583631708` の`linux-glibc-x86_64` archive（SHA-256 `750f0d0396345281295f367bfa8d989effabb99bbfc487e68a14d0dadccd0840`）をPX-Q3U4で確認した。source `591685d89c6eb5283a322f508fa58b2c3759760e` / Core `154e9de7b813cee3cd9db07f22795a4a9e9ae833`。全8 receiverを30秒同時実行し、全client exit 0、client counterは0、stream中statusは8/8 `streaming`、normal daemon停止exit 0、process/FD/socket cleanupに残留なし（空の`.listener.lock` fileのみ）だった。

独立TS解析ではreceiver 0–6のTEIが119,707–315,860、複数receiverにPID continuity discontinuityがあり、client counterのTEI=0と一致しなかった。TS品質条件は不合格。stream中の既存read-only標準APDU照会は10回すべてexit 5でresponseなしとなり、failure=0条件も不合格。receiver 7の同条件reference比較は未実施で判定不能。通常stop/cleanupの合格はTS/APDU不合格を打ち消さない。

各OS/ABIのfinal candidate archive回帰、native Windows/WinSCard、最終candidate由来の2時間・全channel結果は未認定。代表機の全channel10秒試験はLinux x86_64だけに適用し、各binaryで行う短時間回帰と分ける。

## 候補checkpointと確認状況

2026-10-25時点の採用mainは `ef3ce3ec755fcbdf0b5e71bc1ba6d97e05123627`、Core pinは `154e9de7b813cee3cd9db07f22795a4a9e9ae833`。これはsource/pinのcheckpointであり、1.0.0最終candidate archiveの識別ではない。1.0.0向け候補archiveを固定したnative matrix結果はまだ記録されていない。

直近のpin変更時に行ったdevice-free build/testはPX4 source `c7716b5f0d3daab0f1a99a41c334ee53b9224d3b` とCore `154e9de7b813cee3cd9db07f22795a4a9e9ae833` を使った。Linux x86_64 buildでは次を実行し、製品targetと該当testは成功した。

cmake --build build-core108-pin --target px4d px4ctl px4-ts px4_userland_tests px4-ts-product-cli-tests host_ctl_tests host_client_integration_tests -j2

このbuild/testはsource/Core pin確認であり、1.0.0 native release artifactや全OS/機種の検証結果を意味しない。前段のCI runは記録時に未完了で、最終結論は未確認。
